# Технічна специфікація: qlTag (QSP Location Tag editor)

Статус: чернетка (draft) — очікує затвердження перед стартом імплементації.
Підхід: spec-driven development — код не пишеться, доки ця специфікація не закрита і acceptance criteria не узгоджені.

---

## 1. Мета і контекст

`qlTag` — мінімалістичний текстовий редактор для `.qsp`-подібних текстових файлів (quest-код мовою QSP), який живе в `apps/qlTag` цього монорепо поряд з `tools/qsp2ink`.

Естетика і філософія — у стилі редакторів [hundredrabbits](https://100r.co/) (Left, Orca): один портативний файл, без збірки, без фреймворків, монохромний UI, моношрифт, мінімум хрому навколо тексту.

Головна цінність: швидка навігація по великому `.qsp`-файлу через теги локацій (`Location: "id"` / `# id` / `gt 'id'` тощо) — відкрив файл, тапнув по назві локації — редактор проскролив і підсвітив її оголошення.

## 2. Натхнення і UI-принципи (hundredrabbits style)

- Один самодостатній HTML-файл (inline `<style>` + `<script>`), без npm build-кроку.
- Моношрифтовий текст, високий контраст, без декоративних елементів.
- Мінімум UI-хрому: тільки текст + номери рядків + одна кнопка меню.
- Меню не виїжджає анімацією (спрощений overlay/панель, миттєве показати/сховати) — простіше в коді, немає залежності від CSS-transition таймінгів.
- Клавіатура і тап — рівноправні способи взаємодії.

## 3. Область застосування (Scope)

### Входить (In scope)
- Перегляд і редагування одного текстового `.qsp`/`.txt`-файлу за раз.
- Нумерація рядків зліва.
- Рядок з індексом 0 зарезервований під іконку-меню (не є рядком тексту файлу).
- Детекція оголошень локацій у тексті (regex-based, без повного парсингу QSP).
- Тап по рядку з оголошенням локації → скрол/перехід (goto) до цього рядка (по суті — no-op якщо ти вже на ньому, але корисно як "якір").
- Ліве меню (спрощене, без drawer-анімації) з пунктами:
  1. Відкрити (Open)
  2. Зберегти (Save)
  3. Новий файл (New)
  4. Світла/темна тема (Theme toggle) — просто заміна `background`/`color`
  5. Розділювач
  6. Список усіх локацій файлу (тапабельний)
- Тап по локації у списку → закриває меню → автоскрол редактора до відповідного рядка оголошення локації.
- Подвійний тап на слові в тексті → перейменування цього ідентифікатора одразу в усіх місцях відкритого файлу (див. п. 6.6).
- Попередження про незбережені зміни перед виходом/закриттям сторінки (див. п. 6.7).
- PWA: `manifest.json` + service worker для офлайн-роботи й "Add to Home Screen".

### Не входить (Out of scope, явно)
- Повноцінний парсер/лінтер QSP-синтаксису, підсвітка синтаксису (syntax highlighting) — не робимо в v1.
- Виконання/симуляція квесту (execution engine) — це відповідальність `tools/qsp2ink`, не редактора.
- Множинні вкладки/файли одночасно (тому "перейменування по проекту" з п. 6.6 = по всьому єдиному відкритому файлу, не між файлами).
- Undo/redo стек, окрім нативного `contenteditable`/`textarea` браузерного undo (перейменування з п. 6.6 не має власного undo, крім браузерного).
- Пошук/заміна (find & replace) як окрема UI-функція з довільним патерном — можна винести в v2 (довгий-тап-перейменування з п. 6.6 покриває лише сценарій "перейменувати конкретне слово").
- Синхронізація з хмарою/бекендом — файлова робота лише локальна (File System Access API / download-fallback).

## 4. Користувацькі історії

1. Як автор квесту, я відкриваю `.qsp`-файл і бачу текст з номерами рядків, щоб орієнтуватись у файлі так само, як у звичайному редакторі коду.
2. Як автор квесту, я тапаю по іконці меню (рядок 0) і бачу список усіх локацій файлу, щоб швидко знайти потрібну без ручного скролу.
3. Як автор квесту, я тапаю на назву локації в меню — меню закривається, а редактор автоматично скролить і підсвічує рядок з оголошенням цієї локації.
4. Як автор квесту, я тапаю прямо в тексті на ідентифікатор локації (наприклад всередині `gt 'start_L1'`), і редактор переходить (goto) до рядка, де ця локація оголошена — так само як "go to definition".
5. Як автор квесту, я перемикаю світлу/темну тему одним тапом у меню, щоб комфортно редагувати вдень і вночі.
6. Як автор квесту, я зберігаю файл (перезаписую відкритий або качаю новий), не втрачаючи зміни.
7. Як автор квесту, я створюю новий порожній файл, якщо хочу почати писати квест з нуля.
8. Як автор квесту, я можу встановити застосунок на домашній екран телефону і працювати офлайн.
9. Як автор квесту, я подвійним тапом на слові (наприклад назві локації) відкриваю режим перейменування, редагую його, і після тапу осторонь воно змінюється одразу в усіх місцях файлу, де воно вживалось — без ручного пошуку кожного входження.
10. Як автор квесту, я не втрачаю незбережені зміни випадково — при спробі вийти застосунок попереджає мене і дає зберегти файл тим самим шляхом, що й кнопка "Зберегти" в меню.

## 5. Формат виявлення локацій (Location detection)

Redex-набір повинен розпізнавати оголошення локацій у двох реальних форматах, які вже є в репозиторії (`tools/qsp2ink/game.copy.uk.txt`):

| Формат | Приклад оголошення | Regex (оголошення) |
|---|---|---|
| Класичний QSP source | `# start_L1` | `/^#\s*(\S+)/` |
| qsp2ink decompiled export | `Location: "start_L1"` | `/^Location:\s*"([^"]+)"/` |

І посилання (goto references) для розпізнавання "тапу всередині тексту" на ідентифікатор локації:

| Конструкція | Приклад | Regex |
|---|---|---|
| `gt` | `gt 'start_L1'` | `/\bgt\s+'([^']+)'/` |
| `gs` (виклик підпроцедури-локації) | `gs 'showstats'` | `/\bgs\s+'([^']+)'/` |

Пошук локацій виконується один раз при завантаженні файлу і після кожного `Save`/`New` (не на кожен keystroke, щоб не гальмувати друк на великих файлах — дебаунс ~300 мс при редагуванні).

Список локацій для меню = унікальні `id` з таблиці оголошень, у порядку появи в файлі.

## 6. UI-специфікація

### 6.1 Розкладка редактора

```
┌───┬──────────────────────────────────────────┐
│ ☰ │  ← рядок 0: іконка меню замість номера    │
├───┼──────────────────────────────────────────┤
│ 1 │ Location: "_start"                        │
│ 2 │ ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~ │
│ 3 │ Location description:                     │
│ 4 │                                            │
│ 5 │     В'язниця                               │
│ …│ …                                          │
└───┴──────────────────────────────────────────┘
```

- Ліва колонка — номери рядків, моношрифт, тьмяніший колір за основний текст.
- Рядок 0 — не текст файлу, а клікабельна іконка (`☰` / три риски), фіксована зверху (sticky).
- Права область — сам текст, реалізовано як `<textarea>` (нативний елемент, не `contenteditable`) — обрано заради максимальної сумісності "щоб працювало в любому браузері" без додаткового коду під різні DOM-квірки.
- **Перенос рядків без горизонтального скролу**: `white-space: pre-wrap; word-break: break-word;` на `<textarea>` — довгі рядки переносяться візуально, горизонтального скролу немає в жодному елементі інтерфейсу (ні в редакторі, ні в меню, ні в панелі автозаповнення з п. 6.5).
  - Наслідок: один логічний рядок файлу може займати кілька візуальних рядків на екрані. Номер у gutter показується лише навпроти **першого** візуального рядка кожного логічного рядка; продовження (wrap) — порожній рядок у gutter напроти нього.
  - Технічно: висота кожного логічного рядка (скільки візуальних рядків він займає) вимірюється через прихований mirror-`<div>` з ідентичними `font`/`line-height`/`padding`/`width`, `white-space: pre-wrap; word-break: break-word;` (той самий прийом, що й у класичних textarea-based редакторах для wrap-aware gutter). Це чистий DOM/CSS без бібліотек — працює в будь-якому браузері.
- Тап по номеру рядка, що містить оголошення локації (visual highlight — штрихове підкреслення номера, як "анкор" всередині сторінки) → скрол до себе ж / focus (корисно як якірне посилання, наприклад для sharing/deep-link на рядок).
- Тап по ідентифікатору всередині `gt '...'`/`gs '...'` у тексті → якщо знайдено відповідну локацію → плавний (`scrollIntoView`) перехід до рядка з її оголошенням + короткий flash-підсвіт цільового рядка.

### 6.2 Ліве меню (спрощене, без drawer-анімації)

Відкривається тапом по іконці в рядку 0. Реалізація — просте `display: none/flex` (без `transform`/`transition`), перекриває ліву частину екрана або весь екран на мобільному.

```
┌────────────────────────┐
│ Відкрити                │
│ Зберегти                │
│ Новий файл              │
│ ☀ / ☾  Тема             │
│ ──────────────────────  │
│ Локації:                │
│  _start                 │
│  about                  │
│  _onnewloc              │
│  showstats              │
│  ...                    │
└────────────────────────┘
```

- Пункти 1–4 — кнопки дій. "Відкрити"/"Зберегти"/"Новий файл" закривають меню після виконання дії. Тогл теми — виняток: **меню лишається відкритим** після перемикання, щоб одразу можна було тапнути локацію нижче (рішення користувача, див. п. 10).
- Розділювач — `<hr>` або border-top, суто візуальний.
- Список локацій — скролюваний блок (`overflow-y: auto`) нижче розділювача, займає решту висоти меню.
- Тап по пункту локації: (1) закрити меню, (2) `scrollIntoView({block: 'center', behavior: 'smooth'})` на рядок оголошення, (3) короткий flash-підсвіт рядка.

### 6.3 Теми

- Дві теми: light / dark.
- Перемикання — заміна лише двох CSS custom properties: `--bg` і `--fg` (мінімум, як зазначив користувач — "просто заміна бекграунду і кольору тексту").
- Стан теми зберігається в `localStorage` (`qlTag.theme`), застосовується при завантаженні до першого рендеру (щоб уникнути flash-of-wrong-theme).

### 6.4 Файлові операції

- **Відкрити**: `window.showOpenFilePicker()` (File System Access API) якщо доступний; fallback — прихований `<input type="file" accept=".qsp,.txt">`.
- **Зберегти**: якщо файл відкритий через File System Access API — `writable.write()` у той самий handle (перезапис). Якщо fallback-режим (немає File System Access API, напр. Safari/iOS) — `Blob` + `<a download>`.
- **Новий файл**: очищає `textarea`, скидає file handle, скидає список локацій; якщо є незбережені зміни — `confirm()` перед очищенням.

### 6.5 Автозаповнення локацій при вводі `gt '...'` / `gs '...'`

Коли курсор набору тексту перебуває всередині незакритих лапок одразу після `gt '` або `gs '` (наприклад користувач щойно набрав `gt 'escape`), знизу екрана з'являється компактна панель з підказками — до **5** найближчих за фільтром locations.

```
  ...
  gt 'escape▌                              ← курсор
┌──────────────────────────────────────────┐
│ escape_partner_L7                         │
│ escape_cosmo_L8                           │
│ escape_L20                                │
└──────────────────────────────────────────┘
```

- **Тригер**: на кожному `input`/`selectionchange` події перевіряється текст від початку поточного рядка до позиції курсора на збіг з `/\b(?:gt|gs)\s+'([^']*)$/`. Якщо збіг є — це legkий regex по одному рядку (не по всьому файлу), тож рахується без дебаунсу на кожен keystroke. Група 1 — введений наразі префікс (`sPrefix`, може бути порожнім рядком одразу після `gt '`).
- **Фільтрація**: серед `aLocation` (той самий список, що й у лівому меню) шукаються збіги з `sPrefix`:
  1. Пріоритет 1 — `sID.startsWith(sPrefix)`.
  2. Пріоритет 2 — `sID.includes(sPrefix)` (але не `startsWith`).
  3. У межах пріоритету — порядок появи локації у файлі.
  4. Обрізати до перших **5** результатів.
  - Якщо `sPrefix` порожній — показати перші 5 локацій файлу (щоб панель одразу давала підказку навіть до вводу літер).
  - Якщо збігів 0 — панель ховається.
- **Позиціювання панелі**: базово — `position: fixed; bottom: 0; left: 0; right: 0;` (просто, працює у будь-якому браузері без додаткового коду). Як покращення (progressive enhancement, не обов'язкове для MVP) — якщо доступний `window.visualViewport`, слухати його `resize`/`scroll` і виставляти `bottom` так, щоб панель лежала над віртуальною клавіатурою на мобільному, а не під нею.
- **Вибір підказки**: тап/клік по пункту → підставляє повний `sID` замість введеного `sPrefix` між лапками в тексті (курсор ставиться одразу після вставленого ID, перед закриваючою лапкою, яку користувач допише сам або вона додається автоматично, якщо оригінальна конструкція не мала закриваючої лапки), панель ховається.
- Панель — той самий моношрифт/тема, що й редактор; жодних додаткових залежностей.

### 6.6 Подвійний тап на слові → перейменування по всьому файлу (rename-by-word)

Подвійний тап (double-tap) на будь-якому слові в тексті (типовий приклад — назва локації всередині `Location: "id"` або `gt '...'`) вмикає режим перейменування цього ідентифікатора одразу в усьому відкритому файлі. "По всьому проекту" тут = по всьому поточному відкритому файлу — множинних файлів у застосунку немає (див. Scope).

**Чому подвійний тап, а не довгий тап (аналіз заміни жесту):** довгий тап (long-press) конфліктував би з вбудованим нативним жестом браузера в `<textarea>` — лупою (magnifier) і контекстним меню "Копіювати/Вставити", які й самі спрацьовують на довгому утриманні. Подвійний тап такого конфлікту не має: нативна поведінка `dblclick`/double-tap у текстовому полі — це просте виділення слова під точкою дотику (без спливаючих UI-елементів на кшталт лупи чи меню), і ми цю нативну поведінку навіть частково перевикористовуємо як відправну точку для власного визначення меж слова.

**Тригер**
- Слухається нативна подія `dblclick` на `<textarea>` — вона спрацьовує і на подвійний клік мишею (десктоп), і на подвійний тап пальцем на мобільних браузерах (стандартна крос-браузерна поведінка для текстових полів, без ручної реалізації таймінгу подвійного тапу).
- До моменту, коли спрацьовує `dblclick`, браузер уже сам нативно виділив слово під точкою дотику (це його default-поведінка для подвійного кліку на тексті) — `textarea.selectionStart` вже стоїть десь всередині цього слова.
- З цієї точки (`textarea.selectionStart`) межі слова перераховуються **власним** регулярним виразом на юнікод-словесні символи `/[\p{L}\p{N}_]+/u` (а не залишаються нативними межами браузера) — щоб однаково коректно працювати і з латинськими ID локацій, і з кириличними ідентифікаторами на кшталт `Отношение_охраны`, і з підкресленням у складі ID (нативне виділення браузера може трактувати межі слова по-своєму залежно від локалі ОС). Результат — `{ nStart, nEnd, sWord }`, застосовується через `textarea.setSelectionRange(nStart, nEnd)`.

**Компроміс, який варто чесно проговорити (single-tap vs double-tap на одному й тому ж слові):** якщо слово всередині `gt '...'` одночасно підтримує і короткий тап → goto (п. 6.1/AC-5), і подвійний тап → rename, браузер не дає штатного способу дізнатись "це був одиночний клік, чи перший клік подвійного" без короткої затримки. Тому goto-обробник по короткому тапу відкладається на ~300 мс (стандартний поріг розпізнавання double-click/double-tap): якщо за цей час приходить другий тап (спрацьовує `dblclick`) — відкладений goto скасовується і замість нього вмикається rename; якщо другого тапу не було — goto виконується зі невеликою, практично непомітною затримкою ~300 мс. Це усвідомлена ціна за відсутність конфлікту з нативним жестом браузера.

**Взаємодія з іншими жестами (щоб уникнути подвійного спрацювання)**
- Одиночний тап (перший `pointerup`/`click`) запускає відкладений goto-таймер ~300 мс, а не goto одразу (див. компроміс вище).
- Якщо приходить `dblclick` — відкладений goto-таймер скасовується, виконується rename замість goto.
- Поки `bRenameModeActive === true`, панель автозаповнення `gt '...'`/`gs '...'` з п. 6.5 **не показується**, навіть якщо редаговане слово технічно потрапляє в контекст `gt '`/`gs '` — два спливаючі UI-елементи одночасно (рамка перейменування знизу і панель підказок знизу) конфліктували б за простір і увагу користувача.
- Сторінка встановлює `<meta name="viewport" content="..., user-scalable=no">` (чи еквівалент), щоб подвійний тап на тексті не інтерпретувався мобільним браузером як жест "збільшити масштаб сторінки" — стандартна практика для повноекранних редакторів, де подвійний тап має прикладне значення в самому застосунку.

**Візуальний стан (рамка + виділення)**
- `textarea.setSelectionRange(nStart, nEnd)` — нативне виділення слова (підсвітка кольором через `::selection`).
- Поверх `<textarea>` малюється декоративний `<div>` з border (`pointer-events: none`), позиційований по пікселях точно над словом. Координати рахуються тим самим mirror-`<div>`-механізмом виміру, що вже описаний для wrap-aware gutter (п. 6.1), розширеним до обчислення прямокутника довільного діапазону символів — спільна утиліта `getTextRangeRect_ByOffset(nStart, nEnd)`.
- У стан додається: `bRenameModeActive = true`, `sOriginalWord`, `oWordRange`.

**Режим редагування (автозаміна ввімкнена)**
- Поки `bRenameModeActive` активний, ввід символів працює нативно — надрукований текст замінює виділення (стандартна поведінка `<textarea>`, без додаткового коду).
- На кожен `input`-івент, поки режим активний, межі поточного слова під кареткою перераховуються заново (той самий прийом виявлення меж слова, що й у автозаповненні з п. 6.5) — рамка "їде" і змінює ширину слідом за словом, яке зараз редагується.

**Коміт перейменування (тап осторонь)**
- Коли користувач тапає/клікає будь-де поза межами поточного редагованого слова (інша точка в тексті, поза `<textarea>`, втрата фокусу) — режим завершується:
  1. `sNewWord` = поточний текст у відстежених межах слова на момент коміту.
  2. Якщо `sNewWord` непорожній і відрізняється від `sOriginalWord` — усі інші входження `sOriginalWord` у файлі замінюються на `sNewWord` через `\b`-межове, юнікод-аварне регулярне заміщення. Те входження, яке користувач щойно редагував вручну, вже містить `sNewWord`, тому регулярний вираз (шукає `sOriginalWord`) його не чіпає — повторної заміни не станеться.
  3. Рамка ховається, `bRenameModeActive = false`, список локацій перераховується (`getLocationList_ParsedByText`), бо ідентифікатори могли змінитись.
- `Escape` під час активного режиму — необов'язкова, але дешева страховка: повертає `sOriginalWord` на місце введеного тексту і скасовує перейменування без коміту в інші місця файлу.

### 6.7 Попередження про незбережені зміни перед виходом

Користувач описав лише бажаний UX ("конфірм зі своїм текстом Так/Ні, по Так — зберегти як через меню і продовжити вихід"). Нижче — аналіз, що з цього реально можливо в стандартному браузері, і спрощення механізму рівно до того, що можливо.

**Аналіз можливості (по кожному способу вийти окремо):**

| Спосіб вийти | Чи керує сторінка моментом виходу? | Що реально можливо |
|---|---|---|
| Навігація "назад" — апаратна/жестова кнопка Android, swipe-back на iOS Safari, Alt+←/кнопка "назад" браузера | **Так** — це History API-навігація, її можна перехопити до того, як вона фактично станеться | **Повний кастомний UX** — свій текст, свої кнопки Так/Ні, виклик збереження, показ лівої панелі, потім керований вихід |
| Закриття вкладки/вікна/браузера, перехід за новим URL, перезавантаження сторінки, закриття встановленого PWA зі свайп-меню задач | **Ні** — це вихід за межі сторінки, якому DOM/JS не підпорядкований | **Тільки нативний `beforeunload`-діалог браузера.** Сучасні Chrome/Firefox/Safari ігнорують кастомний текст (показують свій generic напис) і не повідомляють JS, яку кнопку обрав користувач. Кастомний `confirm()` всередині `beforeunload` теж заблокований у Chrome. Асинхронне збереження (запис у File System Access handle, формування Blob-download) не гарантовано встигає завершитись, доки браузер закриває сторінку — гарантій нуль. **Це обмеження браузера, не можна обійти жодним кодом.** |

**Висновок / спрощення:** повністю кастомний confirm із програмним збереженням реалізується **тільки для навігації "назад"**. Для реального закриття вкладки/браузера застосунок обмежується нативним попередженням без кастомної логіки — видавати це за щось більше було б введенням в оману.

**Механізм для навігації "назад" (де кастомний UX справді можливий)**

Стандартна SPA-техніка "history guard": поки є незбережені зміни, тримати одну "вартову" позицію в історії, щоб перша спроба піти назад не відпускала зі сторінки одразу, а давала час показати confirm.

1. Коли `bUnsavedChange` вперше стає `true` — `history.pushState({ qlTagGuard: true }, '')` (один додатковий запис в історії поверх поточного).
2. `popstate`-listener: якщо він спрацював і `bUnsavedChange === true` — користувач щойно намагався вийти назад:
   - Одразу повертаємо вартовий запис (`history.pushState({ qlTagGuard: true }, '')` знову), щоб не втратити контроль, поки показується confirm.
   - Показується кастомний confirm:
     ```
     ┌─────────────────────────────────────┐
     │  Бажаєте зберегти зміни?             │
     │                                       │
     │         [ Так ]        [ Ні ]        │
     └─────────────────────────────────────┘
     ```
   - **Так** → `saveFile_ByMenuAction()` — та сама функція, що й пункт "Зберегти" в лівому меню (без дублювання логіки); ліва панель відкривається/лишається відкритою з видимою кнопкою "Зберегти" (візуальне підтвердження + ручний fallback, якщо File System Access API вимагає повторного вибору файлу). Після успіху — `bUnsavedChange = false`, і `history.back()` викликається програмно, щоб фактично завершити вихід, який користувач ініціював.
   - **Ні** → `bUnsavedChange = false`, `history.back()` викликається програмно — вихід завершується без збереження.
   - Якщо `bUnsavedChange === false` на момент `popstate` — вартовий запис не створювався, вихід відбувається природно, без будь-якого попередження.

**Механізм для реального закриття вкладки/браузера (де кастомний UX неможливий)**
- Слухач `beforeunload`: якщо `bUnsavedChange === true` → `event.preventDefault(); event.returnValue = '';` — з'являється нативний діалог браузера. Текст і результат — поза контролем застосунку. Ніякого збереження тут не відбувається і не гарантується.
- Закриття встановленого PWA через свайп у меню задач/диспетчер додатків — теж поза контролем сторінки (жоден JS-event на це не гарантований) — свідомо не покривається, лишається на розсуд ОС/юзера.

Стан: `bUnsavedChange` — виставляється в `true` на кожен `input`-івент у тексті, скидається в `false` після успішного `Save`, після підтвердженого `New` і одразу після `Open`.

## 7. PWA-вимоги

- `manifest.json`: `name: "qlTag"`, `short_name: "qlTag"`, `display: "standalone"`, іконки (мінімум 192/512 px, можна прості SVG→PNG монохромні).
- `sw.js`: cache-first для статичних ассетів (`index.html`, `manifest.json`, іконки) — застосунок повністю функціональний офлайн, бо не має зовнішніх залежностей і мережевих запитів (весь файловий I/O — локальний).
- Реєстрація service worker з `index.html` при завантаженні.

## 9. Технічний дизайн (коротко)

- Ванільний JS, ES2020+, без залежностей.
- Стан застосунку — один об'єкт у пам'яті (без over-engineering зі стором):
  ```js
  const oEditorState = {
    sText: '',              // повний текст файлу
    aLocation: [],           // [{ sID, nLine }], у порядку появи
    oFileHandle: null,       // File System Access API handle або null
    bMenuOpen: false,
    sTheme: 'dark',          // 'dark' | 'light'
    oGotoContext: null,      // { sPrefix, nRangeStart, nRangeEnd } або null, якщо курсор не в gt/gs '...'
    aSuggestion: [],          // до 5 { sID } — поточні підказки автозаповнення
    bRenameModeActive: false, // чи активний режим перейменування по подвійному тапу (п. 6.6)
    sOriginalWord: '',        // слово на момент dblclick, до редагування
    oWordRange: null,         // { nStart, nEnd } — актуальні межі редагованого слова
    bUnsavedChange: false,    // dirty-flag для попередження при виході (п. 6.7)
  };
  ```
- Рендер номерів рядків: окрема колонка, синхронізована по `scrollTop` з `textarea` (класичний прийом lineNumbers gutter), з урахуванням переносу — див. п. 6.1 (wrap-aware gutter через mirror-`<div>`).
- Пошук локацій — функція `getLocationList_ParsedByText(sText)`, що ганяє regex з п. 5 по рядках і повертає `aLocation`.
- Goto — функція `goToLocation_ByID(sID)`: знаходить рядок у `oEditorState.aLocation`, скролить textarea/gutter до нього.
- Wrap-aware gutter — функція `getVisualRowCount_ByLineText(sLine, nTextareaWidth)`: рахує через mirror-`<div>` (offsetHeight поділений на line-height), скільки візуальних рядків займе логічний рядок при поточній ширині textarea; перераховується при resize вікна і зміні тексту (дебаунс ~150 мс).
- Контекст автозаповнення — функція `getGotoContext_ParsedByCaretPosition(sText, nCaretIndex)`: бере підрядок поточного рядка до курсора, матчить `/\b(?:gt|gs)\s+'([^']*)$/`, повертає `{ sPrefix, nRangeStart, nRangeEnd }` або `null`. Викликається без дебаунсу (дешева, один рядок).
- Фільтрація підказок — функція `getSuggestionList_ParsedByPrefix(sPrefix, aLocation, nMax = 5)`: сортує за правилами з п. 6.5 (startsWith → includes → порядок появи), повертає перші `nMax`.
- Вставка підказки — функція `setLocationID_ByGotoContext(sID, oGotoContext)`: замінює `sText.slice(nRangeStart, nRangeEnd)` на `sID`, оновлює `selectionStart`/`selectionEnd` textarea одразу після вставленого ID.
- Межі слова під кареткою — функція `getWordRange_ByCaretPosition(sText, nCaretIndex)`: спільна для подвійного тапу-перейменування (п. 6.6) і, за потреби, для click-to-goto (п. 6.1/AC-5); розширює позицію в обидва боки за `/[\p{L}\p{N}_]+/u`, повертає `{ nStart, nEnd, sWord }`.
- Розпізнавання одиночний/подвійний тап — обробник `click` ставить відкладений `setTimeout(goToLocation_ByTappedWord, 300)`; обробник `dblclick` скасовує цей таймер (`clearTimeout`) і замість goto запускає режим перейменування (п. 6.6).
- Прямокутник діапазону символів — функція `getTextRangeRect_ByOffset(nStart, nEnd)`: той самий mirror-`<div>` з п. 6.1, повертає `{ nLeft, nTop, nWidth, nHeight }` відносно `<textarea>` для позиціювання рамки перейменування.
- Перейменування по файлу — функція `setIdentifier_RenamedEverywhere(sText, sOriginalWord, sNewWord, oSkipRange)`: `\b`-межова, юнікод-аварна заміна всіх входжень `sOriginalWord` на `sNewWord`, окрім діапазону `oSkipRange` (слово, яке вже відредаговане вручну і так містить `sNewWord`).
- Збереження — єдина функція `saveFile_ByMenuAction()` (п. 6.4), яку викликають і пункт меню "Зберегти", і кастомний confirm з п. 6.7 — без дублювання логіки збереження. Після успіху скидає `bUnsavedChange = false`.
- Попередження при виході (п. 6.7): для навігації "назад" — `history.pushState`-вартовий запис + `popstate`-listener з кастомним confirm (повний контроль); для реального закриття вкладки/браузера — лише `window.addEventListener('beforeunload', ...)` з `event.preventDefault()` (нативний generic діалог, без кастомної логіки — обмеження браузера).

## 10. Рішення за відкритими питаннями (затверджено користувачем)

1. **Меню після тогла теми лишається відкритим** — закривається лише вибором локації або тапом поза межами меню/повторним тапом на іконку.
2. Обрано **`textarea`** (не `contenteditable`) — головний критерій — максимальна сумісність з будь-яким браузером і найпростіший код. Детекція кліку по ідентифікатору всередині `gt '...'`/`gs '...'` реалізується через `selectionStart`/визначення меж слова в рядку під курсором кліку — без окремого overlay-шару.
3. Підсвітка рядків-оголошень локацій — **штрихове (dashed) підкреслення номера рядка**, що виконує роль анкора всередині сторінки (як HTML `#anchor`), а не суцільний bold. Дешево і відповідає принципу "все видно одразу".

## 11. Критерії приймання (Acceptance criteria)

**AC-1 Нумерація рядків**
- Given відкритий файл з N рядків, When рендериться редактор, Then зліва показані номери 1..N синхронно з рядками тексту, а рядок з індексом 0 показує іконку меню замість числа.

**AC-2 Меню відкриття/закриття**
- Given редактор відкритий, When тап по іконці в рядку 0, Then ліве меню з'являється миттєво (без анімації-затримки).
- When тап поза межами меню або повторний тап на іконку, Then меню зникає.

**AC-3 Список локацій**
- Given файл містить локації `_start`, `about`, `showstats`, When меню відкрите, Then під розділювачем показаний список саме цих трьох ідентифікаторів у порядку появи в файлі, без дублікатів.

**AC-4 Goto по тапу в меню**
- Given меню відкрите зі списком локацій, When тап по `showstats`, Then меню закривається і редактор автоскролить так, щоб рядок з `Location: "showstats"` (або `# showstats`) був видимий (в ідеалі — по центру екрана).

**AC-5 Goto по тапу в тексті**
- Given у тексті є `gt 'start_L1'` і десь вище/нижче оголошена `Location: "start_L1"`, When користувач тапає по слову `start_L1` всередині `gt '...'`, Then редактор скролить до рядка оголошення `start_L1`.
- Given ідентифікатор без відповідного оголошення в файлі, When тап по ньому, Then нічого не відбувається (no-op, без помилки в консоль користувачу — можна тихий console.warn українською).

**AC-6 Тема**
- Given застосунок у темній темі, When тап по пункту теми, Then фон і колір тексту миттєво міняються на світлу палітру, і вибір зберігається після перезавантаження сторінки (`localStorage`).

**AC-7 Відкрити/Зберегти/Новий файл**
- Given немає відкритого файлу, When тап "Відкрити" і обраний `.qsp`/`.txt`, Then текст файлу рендериться в редакторі з номерами рядків і оновленим списком локацій.
- Given є зміни в тексті, When тап "Зберегти", Then файл перезаписується (File System Access API) або качається як download (fallback), без втрати даних.
- Given є незбережені зміни, When тап "Новий файл", Then показаний підтверджувальний діалог перед очищенням.

**AC-8 Офлайн (PWA)**
- Given застосунок один раз відкритий онлайн (service worker зареєстрований), When мережа вимкнена і сторінка перезавантажена, Then застосунок завантажується і працює (без файлу — стан "порожній редактор").

**AC-9 Перенос рядків без горизонтального скролу**
- Given у файлі є рядок довший за ширину екрана, When редактор рендериться (будь-яка ширина viewport, включно з вузьким мобільним), Then текст переноситься візуально і жоден елемент інтерфейсу (редактор, gutter, меню, панель автозаповнення) не викликає горизонтального скролу сторінки чи власного контейнера.
- Given логічний рядок займає кілька візуальних рядків через перенос, When рендериться gutter, Then номер показаний лише навпроти першого візуального рядка цього логічного рядка, а не навпроти кожного візуального рядка.

**AC-10 Автозаповнення `gt '...'` / `gs '...'`**
- Given курсор набору тексту одразу після `gt '` (наприклад набрано `gt 'escape`), When відбувається ввід символу, Then знизу екрана (або над віртуальною клавіатурою на мобільному, якщо доступний `visualViewport`) з'являється панель максимум з 5 локаціями, чиї `sID` починаються або містять введений префікс, найближчі збіги — першими.
- Given панель підказок відкрита, When тап по одній з підказок, Then текст між лапками замінюється на повний `sID` цієї локації, курсор ставиться одразу після вставленого ID, панель ховається.
- Given курсор виходить за межі `gt '...'`/`gs '...'` (закрив лапку, перейшов на інший рядок), When це відбувається, Then панель підказок ховається.
- Given немає жодної локації, що збігається з введеним префіксом, When це відбувається, Then панель ховається (порожній список не показується).

**AC-11 Подвійний тап → перейменування по всьому файлу**
- Given текст містить слово (наприклад `escape_partner_L7`), When користувач робить подвійний тап на цьому слові, Then слово виділяється і навколо нього з'являється рамка; одиночний тап на тому самому місці такого ефекту не викликає (лише відкладений goto, якщо слово — валідне посилання).
- Given рамка активна над словом, When користувач вводить новий текст, Then виділення замінюється надрукованим текстом (нативна поведінка `<textarea>`), а рамка підлаштовується під нову ширину слова по мірі вводу.
- Given рамка активна і слово відредаговано на нове значення, When користувач тапає в іншому місці тексту (або поза `<textarea>`), Then усі інші входження оригінального слова в файлі замінюються на нове значення, рамка зникає, список локацій у меню оновлюється, якщо змінився ID локації.
- Given рамка активна, When введене нове слово порожнє або збігається з оригінальним, Then заміни по файлу не відбувається (no-op), рамка просто зникає.
- Given рамка активна, When натиснуто `Escape`, Then слово повертається до оригінального значення, заміни по файлу не відбувається.
- Given користувач подвійно тапає на слові усередині `gt '...'`, When спрацьовує `dblclick`, Then goto (AC-5) НЕ спрацьовує (відкладений таймер скасовано) — вмикається лише режим перейменування; і поки рамка активна, панель автозаповнення (AC-10) не показується.
- Given користувач одиночно тапає на слові-посиланні всередині `gt '...'`, When минає ~300 мс без другого тапу, Then виконується звичайний goto (AC-5) — з невеликою, очікуваною затримкою.

**AC-12 Попередження про незбережені зміни перед виходом**
- Given є незбережені зміни, When користувач тапає апаратну/жестову кнопку "назад" (History-навігація), Then реальний вихід не відбувається одразу — показується кастомний confirm "Бажаєте зберегти зміни?" з кнопками Так/Ні.
- Given кастомний confirm показаний, When тап "Так", Then викликається та сама функція, що й пункт "Зберегти" в лівому меню, ліва панель лишається видимою з кнопкою "Зберегти", і після завершення збереження вихід завершується (навігація назад фактично відбувається).
- Given кастомний confirm показаний, When тап "Ні", Then зміни не зберігаються, вихід завершується без збереження.
- Given немає незбережених змін, When користувач тапає "назад", Then жодного попередження не показується, вихід відбувається одразу.
- Given є незбережені зміни, When користувач закриває вкладку/вікно браузера напряму (не через "назад") або перезавантажує сторінку, Then з'являється лише нативний `beforeunload`-діалог браузера з generic текстом — без кастомного Так/Ні і без гарантованого збереження (задокументоване обмеження браузера, не дефект застосунку).

**Примітка до валідації:** AC-12 треба перевіряти вручну на реальному мобільному браузері (жест "назад" / апаратна кнопка), бо емуляція `popstate` в desktop DevTools не завжди повторює поведінку мобільного back-gesture.

## 13. Наступний крок

Усі відкриті питання (розділ 10) закриті користувачем. Довгий тап (long-press) замінено на подвійний тап (double-tap) для перейменування (п. 6.6) саме тому, що подвійний тап не конфліктує з нативними жестами браузера в `<textarea>` (на відміну від long-press, який змагався б із нативною лупою/контекстним меню) — це усуває головний технічний ризик попередньої версії спеки.

Залишковий (значно менший) момент для ранньої перевірки — чи мобільні браузери справді стабільно транслюють подвійний тап у подію `dblclick` на `<textarea>` і чи не заважає цьому viewport-налаштування `user-scalable=no`. Порядок імплементації:

1. **Спершу** — маленький прототип `dblclick`-детекції прямо в `<textarea>` на реальному iOS Safari й Android Chrome (не в емуляторі DevTools), щоб підтвердити коректну поведінку та відсутність конфлікту із зумом сторінки.
2. Далі — решта застосунку одним прямим проходом: `index.html` + `manifest.json` + `sw.js` + іконки, без проміжних фреймворків, згідно з `apps/qlTag/SPEC.md` як єдиним джерелом істини.
